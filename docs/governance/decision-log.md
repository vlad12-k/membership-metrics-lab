# Governance Decision Log

Decisions in this log apply only to the synthetic MemberLoop portfolio. They are not descriptions of Blue Light Card policy.

| ID | Date | Decision | Rationale and alternatives | Impact / validation |
|---|---|---|---|---|
| D-001 | 2026-10-28 | Use half-open effective intervals `[start, end)`; NULL end means open-ended. | Removes ambiguity at adjacent status/eligibility boundaries; inclusive end dates risk double membership. | Test events exactly at interval start/end and prohibit overlapping intervals per entity/key. |
| D-002 | 2026-10-28 | Define active member (30-day) as active on the as-of date with at least one qualifying event in the 30 UTC calendar dates ending on that date. | Distinguishes current eligibility from recent activity; avoids treating any historical event as current activity. | Test `as_of_date - 29`, `as_of_date`, `as_of_date - 30`, and inactive-at-snapshot members. |
| D-003 | 2026-10-28 | Offer redemption rate denominator is distinct eligible member-offer pairs with an offer valid for at least one day in the report period. | A member-only denominator can mix different offer opportunity counts; pair grain aligns numerator and denominator and prevents cross-join inflation. | Numerator is a subset; independently derive the pair set; test pairs with multiple redemptions and zero denominator. |
| D-004 | 2026-10-28 | Partner engagement denominator is active partners with at least one active offer and at least one eligible member opportunity during the period. | A partner with no available offer cannot reasonably be classified as non-engaged for the rate. | Deduplicate partner set before counting; validate numerator subset and category attribution. |
| D-005 | 2026-10-28 | Cohort is registration calendar month; age 0 is registration month; use fixed eligible cohort size as denominator. | Keeps cohort assignment stable and avoids denominator shrinkage hiding attrition. | Exclude right-censored/incomplete follow-up periods from comparisons; do not force missing months to zero. |
| D-006 | 2026-10-28 | Event/redeemed time is stored/attributed in UTC; use UTC calendar periods in v1. | Avoids mixed local timezone/daylight-saving semantics in a synthetic cross-region example. | Exercise UTC boundary tests; local civil-time reporting is explicitly out of scope for v1. |
| D-007 | 2026-10-28 | Preserve distinct row grains for source redemptions, member-offer eligibility and member events; pre-aggregate before joining independent event streams. | Prevents accidental multiplication of redemption counts from many-to-many joins. | Uniqueness tests at each grain; add regression examples that fail if joins fan out. |
| D-008 | 2026-10-28 | Use local PostgreSQL + dbt Core v1 + Lightdash rather than local DuckDB + Lightdash. | Direct PostgreSQL connector is documented; ordinary DuckDB file integration would require MotherDuck or a DuckLake configuration. | Full architecture reasoning: [`../adr/0001-local-postgres-lightdash.md`](../adr/0001-local-postgres-lightdash.md); live PostgreSQL/Lightdash connection remains a later gate. |
| D-009 | 2026-10-28 | All current KPI definitions are proposed v1.0 project semantics; metric owners are fictional roles. | Avoid implying real-company policy or stakeholder agreement. | Every future semantic change records owner rationale, technical impact, tests, effective date and version history. |
